# 校园寻物局｜项目分析报告与参赛规划

版本：v1.1 · 日期：2026-10-03 · 面向：三人参赛团队

## 1. 项目摘要

校园寻物局是基于地图线索与智能匹配的校园失物协作平台，连接学生和保卫科、宿管、失物保管点等相关工作人员。

核心流程：**发布寻物或登记拾获 → 推荐候选 → 展示依据 → 提交私密认领证据 → 工作人员核验 → 确认归还。** 无可靠候选时，补充路线或线索并申请协助工单。

参赛目标为学生赛道一至三等奖。主张通过完整产品、真实码道开发记录、公平效果评估和稳定演示建立竞争力。

**当前状态：仅有规划资料，尚未在本包中完成开发或效果验证。** 需求以场景分析形成假设，外部参与不作为开发或验收的前置条件。

## 2. 需求、价值和竞争风险

| 方面 | 当前判断 | 验证或控制措施 |
|---|---|---|
| 学生查找候选 | 信息可能分散，痛点强度尚未验证 | 建立典型事件和查找任务，记录团队模拟的耗时与操作问题 |
| 拾获与保管 | 需要供给侧登记，否则匹配无数据可用 | 设计登记、保管和认领流程，以演示事件检查闭环；真实入口待验证 |
| 地图价值 | 有展示力，但可能增加发布负担 | 团队任务测试检查空间线索是否可用，不据此推断真实用户收益 |
| 智能匹配 | 有机会改善模糊描述检索 | 与同等输入和候选库的关键词基线比较 |
| 认领安全 | 相似物品推荐不能证明所有权 | 私密特征加人工核验，保留交接确认 |
| 校方资源 | 暂无地图和监控授权 | 自绘或合法底图，明确模拟点位和业务流程 |
| 运营 | 属于低频需求，双方记录来源是关键 | 将一栋楼或一个保管点作为后续试点设想，本届不以试点开展为交付前提 |

建议执行：保留选题，采用局部场景完成产品。游戏化用于交互风格，匹配和核验作为业务主线。独创性尚未完成竞品核验，不宣称全国首创、精准定位失物或自动调取监控。

场景规格覆盖四类事件：明确知道丢失地点、只记得经过路线、已拾获等待认领、直接匹配失败需要协助。每类写清角色、输入、操作、结果、异常与隐私要求，并建立“假设—设计依据—对应功能—验证方式—剩余不确定性”记录。

团队测试能验证功能与流程，不等于外部需求认可。正式材料使用“针对校园寻物场景设计”，不将假设写成学生普遍需求或校方已认可。

## 3. 评分依据及项目应对

初赛评分：功能完备度 30、码道深度使用 25、专业贴合与创新 25、技术架构与工程质量 15、交付规范性 5。

决赛评分：作品核心质量 35、码道应用深度 20、现场演示与答辩 30、创新与落地价值 15；介绍 5 分钟、提问 3 分钟。

评分与提交要求依据[官方赛题页](https://developer.huaweicloud.com/competition/information/1300000338/circumstance)。详见[评分与验收清单](评分与验收清单.md)。内部 87 分目标用于自查，不是官方成绩预测或获奖分数线。

必须以华为云码道为核心 AI 编程工具，真实记录规格、设计、实现、排错、测试和文档过程。产品运行时的物品理解与匹配采用独立模型接口，其调用不等于码道使用证明。

专业贴合与创新重点提交场景假设、空间线索、证据卡、核验机制和公平对照。取消外部需求验证后，真实场景支撑会减弱；内部模拟不能补足这部分证据，也不能据此推断官方固定扣分或获奖概率变化。

## 4. 产品范围

| 模块 | 第一版范围 |
|---|---|
| 地图 | 一个室外示意图、一栋楼两层；缩放、标点、室外画圈、分层路线 |
| 大厅 | 寻物、拾获列表及类别、地点、时间、状态筛选；关联地图 |
| 发布与匹配 | 图片与文字提取、用户确认、最多三个候选及解释 |
| 认领归还 | 私密证据、工作人员核验、交接确认、关闭记录 |
| 协助工单 | 接单、授权线索、模拟点位、核查清单、结果反馈 |
| 我的委托 | 本人发布、申请和协助进度；轻量协助徽章 |

本届不纳入真实视频、人脸识别、自动追踪、3D 校园、全校楼层、开放聊天和积分商城。

学生端采用游戏委托卡和轻量卡通图标；工作人员端采用清晰工单。视觉投入控制在约 20 人时，优先可读性和移动端操作。

## 5. 角色、状态和隐私

学生负责发布、登记拾获、提交线索、申请认领和申请协助。工作人员负责核验、接单、保管信息及归还确认；工作人员角色不能自行注册获取。

| 对象 | 状态 |
|---|---|
| 寻物 | 寻找中、核验中、已找回、已撤销 |
| 拾获 | 待认领、核验中、已归还、已撤销 |
| 认领 | 待审核、已通过、已拒绝、已完成 |
| 工单 | 待接单、处理中、已反馈 |

核验失败后相关记录恢复可处理状态。同一物品可有多个申请，但只能完成一次归还；工作人员核验，拾获者配合确认交接。AI 不决定所有权。

公共数据：用户确认公开的物品描述、图片、时间地点和记录状态。私密数据：联系方式、认领依据、未公开特征和自述路线。本人访问自己的私密数据；路线只有主动授权并分配给该工单的工作人员可访问。

模拟点位仅工作人员可见。点位距离不代表摄像头覆盖范围，拥有点位不意味着获得视频调取权限。

## 6. 技术与匹配规划

技术栈：React＋TypeScript、FastAPI、PostgreSQL、Docker Compose、Leaflet 图片图层；单体架构，不训练模型，不增加独立向量数据库。

数据对象：用户、图层、寻物/拾获、线索、认领、工单、模拟点位和徽章。接口负责发布筛选、地图读取、特征提取、候选匹配、核验归还及工单操作。后端权限、归还事务和重复请求处理是必要验收项。

地图保存图层、版本和归一化坐标，跨楼层路线分段；无比例尺时不显示米数。

模型优先采用华为云 MaaS 图像理解与文本向量能力，阶段 1 验证实际账号和费用。官方可用能力见[MaaS 模型说明](https://support.huaweicloud.com/model-call-maas/model-call-050.html)。不假设赛事开发体验权限包含产品运行时模型额度。

特征包括类别、颜色、品牌、形状和独特标记；无法判断留空，用户确认后参与匹配。初始权重为语义 60%、特征 25%、时间 10%、地点 5%，缺失项归一化。仅用户确认的明确类别冲突可排除，地点不作硬过滤。

证据卡显示一致、冲突、缺失和时间地点关系；排序分数不是找回概率。阈值仅在验证集确定。同款物品仍需人工核验。

限制上传与调用量，密钥只存后端，发送物品图片和描述前取得明确确认。未配置、超时、额度不足时保留手动流程；规则、缓存、模型结果分别标识。

## 7. 码道开发与团队工作

统一采用码道 IDE。流程为规格、设计、任务、实现、验证，每阶段人工确认。结合项目 Rules 和一项业务验收 Skill，避免为展示工具增加无关架构。

| 成员 | 主要责任 |
|---|---|
| A | 前端、地图、交互及移动端 |
| B | 后端、权限、数据库、状态及部署，由完整项目经验最强者承担 |
| C | AI、评估、开发证据、材料及演示统筹 |

每个模块由另一名成员复核，每两天形成可运行版本。每阶段保存 Prompt、修改、人工判断、实际测试及对应提交，重点整理真实排错和需求变化案例。不把其他工具草稿包装成码道成果。

码道能力参考：[规范驱动开发](https://support.huaweicloud.com/bestpractice-codeartsagent/codeartsagent_bp_0011.html)、[Rules](https://support.huaweicloud.com/usermanual-codeartsagent/codeartsagent_ug_0019.html)、[Skills](https://support.huaweicloud.com/usermanual-codeartsagent/codeartsagent_ug_0024.html)。

## 9. 验证与获奖判断

场景与假设检查：四类事件均有规格和验收用例，设计依据与未证实判断分开。测试发现的问题驱动修正，不把流程通过当作真实需求已获验证。

团队角色模拟：成员使用不同账号扮演学生和工作人员，实际执行发布、查找、认领、核验、归还与工单任务，记录步骤、耗时、错误、卡点及修复。取消外部参与人数门槛；记录明确标记为内部模拟，不称为真实用户试用。

匹配评估：约 100 条拾获记录、40 条查询，30 条有对应物品、10 条无对应物品；验证集 10＋5，测试集 20＋5。按物品身份分组；固定候选库，公平比较关键词与推荐，只在验证集调参。

目标：测试 Top-3 至少 16/20 命中，相比关键词基线提高至少 10 个百分点，同时报告无匹配误推荐、实际耗时及失败案例。目标不是当前结果，小样本不代表全校找回率。

工程验收和提交要求见配套清单。连续完成 10 次主流程并分别记录，验证干净环境启动；校方授权、需求认可及真实使用效果保持待验证。测试记录只证明实际执行的范围。

此前一至三等奖 20%–35% 仅为特定参赛规模和交付水平下的主观参考；缺少竞争作品和实测交付，不能可靠计算本队胜率，也不放入正式参赛材料。规划依据应是产品、码道、评估和展示证据。

置信度：中。官方评分已有来源，执行范围可控；资源、真实需求和效果仍需验证。
