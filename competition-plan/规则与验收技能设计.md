# 码道项目规则与业务验收 Skill 设计

这是供阶段 2 配置的设计稿，**未创建、安装或启用任何码道规则或技能**。具体配置方式以团队使用的码道版本官方文档为准。

## 1. 项目级 Rules 内容

可将以下内容作为码道项目规则文本：

```text
# 校园寻物局项目约束

技术栈：React＋TypeScript、FastAPI、PostgreSQL、Docker Compose、Leaflet 图片地图，单体架构。

- 工作人员权限在后端检查，不能自行注册获取。
- 公开接口不返回联系方式、私密特征、认领证据或路线。
- 路线默认本人可见，主动授权且工单分配后处理人员可见。
- AI 只提取与推荐，用户确认特征，工作人员核验所有权。
- 同一物品只完成一次归还；相关状态更新具有事务和重复请求处理。
- 模拟点位、规则推荐、缓存结果和实时模型分别标明来源。
- 点位距离不代表覆盖范围，无比例尺的地图不显示米数。
- 密钥只存后端，不出现在代码、日志、截图或对话中。
- 不把私密证据、联系方式或路线作为模型输入。
- 模型故障不阻断手动发布、筛选、核验和归还。
- 不接入真实视频，不增加无关框架、商城、3D或自动追踪。
- 修改业务状态同步检查权限、异常与回归场景。
- 只报告实际执行结果；真实、模拟、目标和未验证项分别标记。
- 需求来自场景分析，未证实判断标为假设；团队模拟不代表真实用户认可。
- 每次任务限定范围，输出改动、实际验证、未解决项和证据索引。
```

## 2. Skill 的职责

名称：校园业务验收。触发时机：变更角色、公开/私密字段、状态、地图保存、模型降级、工单或准备阶段交付时。

输入：确认规格、验收清单、本次代码差异、可用测试命令及环境说明。输出：检查表、实际测试结果、可复现问题、未执行原因和修复建议。

流程：

1. 阅读已确认规格与本次差异，确认变更范围。
2. 将变更映射到验收场景，选择必要检查。
3. 检查后端权限、状态、事务、图层、模型来源和故障行为。
4. 在可用环境执行检查，命令和输出保留；缺环境就标记未执行。
5. 对失败提供复现步骤与最小修复建议；不能用猜测代替测试结果。
6. 输出通过、不通过、未执行及不适用项，阶段是否通过由人工决定。

## 3. 重点检查矩阵

| 范围 | 场景 |
|---|---|
| 权限 | 学生越权、其他学生读取私密信息、未授权工作人员读路线 |
| 归还 | 未核验、重复提交、多申请和状态冲突 |
| 地图 | 保存刷新、楼层切换、跨层片段及无比例尺 |
| 模型 | 未配置、超时、解析失败、额度耗尽及来源标识 |
| 工单 | 本人申请、分配授权、结果反馈和重复徽章 |
| 真实性 | 目标冒充结果、需求假设冒充用户结论、模拟冒充真实或来源不明 |

技能引用确认后的清单，不新增业务规则，不自动购买、发布或提交参赛材料。

场景依据与团队模拟记录纳入真实性检查，外部人员参与及需求认可不作为本计划阶段通过的必需条件。
